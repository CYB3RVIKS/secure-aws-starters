# Identity and Access Management (IAM)

## What is IAM?

**Identity and Access Management (IAM)** is an AWS service used to control **who can access AWS resources and what they are allowed to do**.

IAM manages two important security concepts:

* **Authentication** — Who are you?
* **Authorization** — What are you allowed to do?

---

## IAM Identities

The main IAM identities are:

1. **Users**
2. **Groups**
3. **Roles**

### 1. Users

An IAM user represents a person or application that needs to interact with AWS resources.

By default, an IAM user has **no permissions** until permissions are granted through IAM policies.

### 2. Groups

A group is a collection of IAM users.

Groups make permission management easier. Instead of attaching the same policy individually to multiple users, users can be placed into a group and the permissions can be assigned to the group.

**Example:**

A company has five developers who all need access to the same AWS services.

Instead of giving each developer the same policies individually:

`Developer 1 → Policy`
`Developer 2 → Policy`
`Developer 3 → Policy`
`Developer 4 → Policy`
`Developer 5 → Policy`

We can create:

`Developers Group → Policy`

and add all five users to the group.

### 3. Roles

An IAM role provides **temporary credentials and permissions** that can be assumed by a trusted entity.

Roles are commonly used when:

* An AWS service needs to access another AWS service.
* A user needs temporary elevated permissions.
* An application needs access to AWS resources.
* Users from another AWS account need controlled access.

---

# IAM Policies

An IAM policy is a document that defines **what actions an identity is allowed or denied to perform on AWS resources**.

Policies are used to grant or restrict access.

### Principle of Least Privilege

Always give users, applications, and services **only the permissions they need to perform their tasks—and no more**.

For example:

If a user only needs to read objects from an S3 bucket, they should not automatically receive permissions to delete buckets or modify IAM users.

> **Least privilege reduces the potential impact of compromised accounts.**

---

# Authentication and Authorization

### Authentication

Authentication verifies **who you are**.

Example:

> Logging into AWS using your username and password.

### Authorization

Authorization determines **what you are allowed to do** after you have been authenticated.

Example:

> You are authenticated, but your IAM policy determines whether you can create an EC2 instance.

**Easy way to remember:**

`Authentication = Who are you?`

`Authorization = What can you do?`

---

# Multi-Factor Authentication (MFA)

**MFA** adds an additional layer of security to an AWS account.

Instead of relying only on a password, MFA requires another authentication factor, such as a code generated by an authenticator device or app.

MFA should be enabled, especially for the **AWS root user** and privileged IAM identities.

### Root User Security

The AWS root user has extensive access to the AWS account and should **not be used for everyday tasks**.

The root user's credentials should be protected carefully, and MFA should be enabled.

For normal administrative and operational tasks, use appropriate IAM identities and roles instead.

> **Never use the root user as your everyday AWS account.**

# AWS Permission Model

AWS permissions follow a default-deny model.

### Implicit Deny

If there is no policy that allows an action, the action is **implicitly denied**.

Example:

A user tries to create an EC2 instance but has no policy allowing `ec2:RunInstances`.

**Result:** Access is denied.

### Explicit Allow

An explicit `Allow` grants permission to perform a specific action.

Example:

```text
Effect: Allow
Action: s3:GetObject
Resource: ...
```

This allows the specified S3 action, assuming there is no applicable explicit deny.

### Explicit Deny

An explicit `Deny` specifically blocks an action.

An explicit deny **overrides an allow**.

Example:

```text
Effect: Deny
Action: s3:DeleteObject
Resource: ...
```

Even if another policy grants `s3:DeleteObject`, the explicit deny takes precedence.

### Permission Evaluation — Simple Rule

Think of it as:

```text
Default → Deny

Explicit Allow → Permission granted

Explicit Deny → Permission denied
                 ↓
          Overrides Allow
```

# Key Takeaways

* **IAM controls access to AWS resources.**
* **Authentication** verifies identity.
* **Authorization** determines permissions.
* **Users** represent identities that need access.
* **Groups** organize users and simplify permission management.
* **Roles** provide temporary credentials and permissions.
* **Policies** define permissions.
* Follow the **Principle of Least Privilege**.
* Enable **MFA**, especially for privileged access and the root user.
* Avoid using the **root user for everyday tasks**.
* AWS follows a **default implicit deny** model.
* An **explicit allow** grants permission.
* An **explicit deny** overrides an allow.

## Security Question

### Why shouldn't everyone have AdministratorAccess?

Because AdministratorAccess gives extremely broad permissions.

If an account with administrator privileges is compromised, an attacker could potentially access, modify, or delete large portions of the AWS environment and cause significant security and financial damage.

**Least privilege limits the blast radius of a compromised account.**
